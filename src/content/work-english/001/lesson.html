原文

Summary本期必读

01Be kind.

01Explain your reasoning.

02Balance giving explicit directions with just pointing out problems and letting the developer decide.

03Encourage developers to simplify code or add code comments instead of just explaining the complexity to you.

Courtesy本期必读

04In general, it is important to be courteous and respectful while also being very clear and helpful to the developer whose code you are reviewing. One way to do this is to be sure that you are always making comments about the code and never making comments about the developer. You don’t always have to follow this practice, but you should definitely use it when saying something that might otherwise be upsetting or contentious. For example:

05Bad: “Why did you use threads here when there’s obviously no benefit to be gained from concurrency?”

06Good: “The concurrency model here is adding complexity to the system without any actual performance benefit that I can see. Because there’s no performance benefit, it’s best for this code to be single-threaded instead of using multiple threads.”

Explain Why本期必读

07One thing you’ll notice about the “good” example from above is that it helps the developer understand why you are making your comment. You don’t always need to include this information in your review comments, but sometimes it’s appropriate to give a bit more explanation around your intent, the best practice you’re following, or how your suggestion improves code health.

Giving Guidance本期必读

08In general it is the developer’s responsibility to fix a CL, not the reviewer’s. You are not required to do detailed design of a solution or write code for the developer.

09This doesn’t mean the reviewer should be unhelpful, though. In general you should strike an appropriate balance between pointing out problems and providing direct guidance. Pointing out problems and letting the developer make a decision often helps the developer learn, and makes it easier to do code reviews. It also can result in a better solution, because the developer is closer to the code than the reviewer is.

10However, sometimes direct instructions, suggestions, or even code are more helpful. The primary goal of code review is to get the best CL possible. A secondary goal is improving the skills of developers so that they require less and less review over time.

11Remember that people learn from reinforcement of what they are doing well and not just what they could do better. If you see things you like in the CL, comment on those too! Examples: developer cleaned up a messy algorithm, added exemplary test coverage, or you as the reviewer learned something from the CL. Just as with all comments, include why you liked something, further encouraging the developer to continue good practices.

Label Comment Severity选读

12Consider labeling the severity of your comments, differentiating required changes from guidelines or suggestions.

13Nit: This is a minor thing. Technically you should do it, but it won’t hugely impact things. Optional (or Consider): I think this may be a good idea, but it’s not strictly required. FYI: I don’t expect you to do this in this CL, but you may find this interesting to think about for the future.

14This makes review intent explicit and helps authors prioritize the importance of various comments. It also helps avoid misunderstandings; for example, without comment labels, authors may interpret all comments as mandatory, even if some comments are merely intended to be informational or optional.

Accepting Explanations选读

15If you ask a developer to explain a piece of code that you don’t understand, that should usually result in them rewriting the code more clearly. Occasionally, adding a comment in the code is also an appropriate response, as long as it’s not just explaining overly complex code.

16Explanations written only in the code review tool are not helpful to future code readers. They are acceptable only in a few circumstances, such as when you are reviewing an area you are not very familiar with and the developer explains something that normal readers of the code would have already known.

重点段落中文对照

01 通常，在评审代码时，你既要礼貌、尊重地对待开发者，也要让反馈清楚且有帮助。

02 一种做法是确保你始终在评价代码，而不是评价开发者本人。

03 不必在所有情况下都遵循这个做法，但当你说的话可能令人不快或引发争议时，一定要这样做。例如：

不佳：“既然并发显然没有任何好处，你为什么还在这里使用线程？”

较好：“这里的并发模型增加了系统复杂度，但我没有看到实际的性能收益。既然没有性能收益，这段代码最好改为单线程，而不是使用多个线程。”

先自己写两句话，再看参考表达。
工作场景

同事的项目报告信息齐全，但客户不容易快速找到关键发现。请用英语建议对方调整报告。

请用英语写两句话：

“这份报告有些难以快速浏览。我们能否把关键发现放在第一页，让客户更容易找到重点？”

写完后，查看参考表达

The report is a little difficult to scan. Could we put the key findings on the first page so the client can find the main points more easily?

你的第一句描述阅读困难；示范把它具体说成 key findings are hard to locate，意思相同。

看完整对话：同事追问详细数据怎么处理

Before a client meeting

Maya is reviewing a project report with her colleague, Alex. The report includes all the necessary information, but the main findings are hard to locate. Instead of criticizing Alex, Maya explains what the reader needs.

“Thanks for putting this together. Could we put the key findings on the first page so the client can review them quickly?”

Alex asks whether he should remove the detailed data. Maya replies, “Let's keep it in the appendix. That way, the client can check the details without losing sight of the main points.”

Maya 正和同事 Alex 一起检查项目报告。报告信息齐全，但主要发现不好找。她没有批评 Alex，而是说明读者需要什么。

“谢谢你整理这份报告。我们能否把关键发现放在第一页，让客户更快查看？”

Alex 问是否应该删掉详细数据。Maya 回答：“我们把数据保留在附录里吧。这样客户可以查看细节，又不会忽略重点。”

把建议说完整

记住这条表达顺序：指出问题 → 提出建议 → 说明好处。实际沟通时，可以按情况调整。

指出问题

The report is a little difficult to scan.

这份报告有些难以快速浏览。

提出建议

Could we put the key findings on the first page?

我们能否把关键发现放在第一页？
Could we + 动词原形 用来提出建议。

说明好处

… so the client can find the main points more easily.

这样客户就能更容易找到重点。
so + 主语 + can 说明这样做的作用。

八、换个场景再写：给演示文稿提建议

写两句话：指出演示文稿的问题，提出具体改法，并说明这样做对听众的帮助。

同事的演示文稿包含太多细节，听众不容易抓住重点。请建议先展示关键发现，并把详细数据放进附录。

查看参考答案与解析

The presentation is difficult to follow because it has a lot of detail. Could we lead with the key takeaway and move the supporting data to an appendix so the audience can follow the main points more easily?

第一句说出演示文稿给听众造成的困难；第二句提出调整，并用 so 说明调整后的作用。lead with 表示先呈现最重要的信息。

还可以换一种说法。检查信息是否准确、建议是否具体、语气是否合适。
