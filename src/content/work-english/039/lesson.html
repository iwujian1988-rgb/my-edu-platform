Types and Examples of Non-Inclusive Code Review Behavior

Inequitable review assignments.

Example: Assigning most reviews to few people and dismissing some members of the team altogether.

Negative interpersonal interactions.

Example: Long arguments over subjective topics such as code style.

Biased decision making.

Example: Comments about the developer and not the code. Assuming code from developer X will always be good and hence not reviewing it properly and vice versa.

Examples of Inclusive Code Reviews

Anyone and everyone in the team should be assigned PRs to review.

Reviewer should be clear about . Arguments over personal preferences and opinions are mostly avoidable.

Using inclusive language and tone in the code review comments. For example, in the review comments is a good way to get the point across the table.

It's a good practice for the author of a PR to thank the reviewer for the review, when they have contributed in improving the code or you have learnt something new.

Guidelines for the Author

Using the sandwich method for recommending a code change to a new developer or a new customer: . For example: "Great work so far, but I would recommend a few changes here. Btw, I loved the use of XYZ here, nice job!"

Aim to write a code that is easy to read, review and maintain.

It’s important to ensure that whoever is looking at the code, whether that be the reviewer or a future engineer, can understand the motivations and how your code achieves its goals.

Proactively asking for targeted help or feedback.

Respond clearly to questions asked by the reviewers.

Guidelines for the Reviewer

Avoid huge commits by submitting incremental changes. Commits which are large and contain changes to multiple files will lead to unfair review of the code. Biased behavior of reviewers may kick in while reviewing such PRs. For e.g. a huge commit from a senior developer may get approved without thorough review whereas a huge commit from a junior developer may never get reviewed and approved.

同事提交的注册表单在邮箱栏为空时只显示笼统错误。请在代码评审中建议一个具体改动，说明它能怎样帮助用户，并用问题邀请作者一起判断。

查看参考表达

Could we show a clear message when the email field is blank? That would help users correct the form before submitting. What do you think about this change?

评论先提出针对代码行为的具体建议，再说明用户收益，最后邀请作者回应，而不是下命令或评论作者。

情景练习（模拟） · Suggest a code change without dictating it

You are reviewing a teammate PR for a sign-up form. When the email field is blank, the form returns a generic error and gives the user no clear next step.

Suggest a specific change that addresses the behavior, explain the user benefit, and leave room for the author to respond.

Keep the comment about the code and user experience, not the author ability or personal style.

查看场景中文

你正在评审同事提交的注册表单代码。邮箱栏为空时，表单只返回笼统错误，没有告诉用户下一步怎么做。

请提出具体修改建议，说明对用户的帮助，并给作者留下回应空间。

评论要针对代码行为和用户体验，不评价作者能力或个人风格。

04

语法拆句

原文句子

Be suggestive and not prescriptive.

  • 这是一个祈使句，省略了主语 you；Be 后接形容词 suggestive 和 prescriptive，and 连接正反两种评论方式。
  • 这里不是要求评论者含糊其辞，而是建议用询问或建议表达具体问题，避免命令作者。
  • 接下来的原文说明作者可以自行决定是否接受修改建议。
换到工作场景

A helpful review comment identifies an observable behavior, suggests a possible change, explains its impact, and invites discussion.

05

句式仿写

比较两种写法，再试着换成自己的工作内容。

原来的写法

This code is incomprehensible. Rewrite it now.

修改后的写法

Could we walk through what this branch is intended to do? I may be missing context, and understanding its purpose would help me review the edge cases.

我们能否一起看一下这段分支逻辑原本要处理什么？我可能缺少一些上下文，了解它的目的会帮助我检查边界情况。

试着替换信息
Could we [ask a specific question]? I may be missing context, and [understanding it] would help me [review the code].

Try a suggestive question instead of a direct order.

试着用建议式问题，而不是直接下命令。
